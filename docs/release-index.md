# SeeWow 版本汇总（1.0.0 → 1.21.8）

> 生成日期：2026-11-17，2026-11-19 补 1.20.1，2026-11-23 补 1.21.4，2026-11-24 补 1.21.5、1.21.6，2026-11-25 补 1.21.7、1.21.8 · 数据来源：GitHub Releases API（`gh release view`）+ `git tag` + `docs/releases/*.md`
> 用途：把散在 16 个预发布里的内容收成一张表，任何人不用翻 Release 页就能回答"哪一版有什么""哪个平台现在能装什么"。

## 1. 一句话现状

从 1.0.0（11-05）到 1.18.0（11-15），**11 天发了 17 个 1.x 版本 + 1 个 Rust 验收包**；其中 16 个标记 Pre-release，只有 1.0.0 与 1.1.0 是正式标记。**这个问题已在 1.19.0 修正**：首页默认下载早就不再指向 1.1.0。1.20.0 与 1.20.1 三端均已出包（macOS / iOS / Android）。1.21.3 与 1.21.4 都已发版（11-23）：`v1.21.3` 出 macOS + iOS 两份零源公开包，`v1.21.4` 只出 macOS 公开包（tag 是在 `b25ada3` 上补的，代码与 1.21.4 不同版）。`gh api releases/latest` 现在返回 `v1.21.8`（11-25）：公开包不再随包带内置源，macOS 包从 124 MB 回到 42.7 MB。平台覆盖每版都不一样：1.21.5 是第一次**五端在同一个 tag 上全部构建通过**（公开资产四份——iOS 未签名包装不上，留在本机），但在此之前没有任何一版同时出齐五个平台。1.21.7 与 1.21.8 也做到了同一件事（同一 tag 五端构建通过、四份公开资产）——**1.21.8 与 1.21.7 是同一份代码的两次出包**：只有版本号从 33 变成 34，目的是把本机 app（此前停在 1.21.6）、iCloud 的 iOS 包（1.21.6）与 Release 资产（1.21.7）对齐到同一个号。

**读法与结论**

- **资产层面的五端齐全只出现过两次**：1.1.0 与 1.17.0。1.16.0 缺 Android，1.18.0 只有 macOS + iOS。
- **1.21.5（11-24）是第一次「同一 tag 五端构建通过」**：run 45393606265 六个 job 全绿，公开资产四份（macOS / Windows / Linux / Android），iOS 未签名包按规则不进 Release。这也是第一次由 CI 在打 tag 时自动建 Release、自动传资产——前面每一版的包都是本机打好再传的。
- **Windows / Linux 断档最长**：1.1.0 → 1.16.0 中间 12 个版本没有包。
- **1.18.0 没有 SHA256SUMS.txt**，校验值只写在发布说明正文里，机器不好用。
- 1.18.0 的说明里已如实写「Android / Windows / Linux 仍是 1.17.0」，这一句是对的；问题在首页与 Latest，不在说明。

## 4. 发布说明自身的结构问题

- **17 份说明没有索引**：只能从 README 或 Release 页一个个点进去。本文第 2 节就是补这个缺口。
- **没有 CHANGELOG.md**：用户想"从 1.10 升到 1.18 有什么变化"只能读 9 份文档。
- **版本号语义不清**：1.x 里既有功能版（1.16）也有纯修复版（1.18），但版本号只递增 minor，没有 patch 位来表达"只修 bug"；用户无法从号判断要不要升级。
- **"Pre-release" 用满了**：17 个全标预发布，只有 1.0.0/1.1.0 是正式标记，导致 Latest 机制失效——这正是首页指向 1.1.0 的原因。

## 5. 建议（已写入路线图）

1. 把 Latest 指向当前可用的最新预览版（1.18.0），其余保持 Pre-release。
2. 每次发布必须五平台齐全或明确列出缺口，并附 SHA256SUMS.txt。
3. 建立 `CHANGELOG.md`，一行一版，指向详细说明。
4. 1.x 启用第三位：`1.19.0` 修资源管理，之后 `1.19.1` 只修缺陷。
5. 发布说明加一节固定标题「本版未修」，把已知缺陷写在明面上，而不是只写"未做的新功能"。
