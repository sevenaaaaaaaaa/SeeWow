## 1. 改了什么

### 1.1 macOS 包的三倍体积：upload-artifact 把符号链接写成真文件

症状：1.21.3 是 42,505,967 字节、1.21.4 是 42,605,558，1.21.5 跳到 124,150,561。

定位过程按顺序记下来，因为前两步都在排除假设：

1. **打包工具** —— 本机把同一份 bundle 分别用 `ditto`（本机脚本用的）和 `zip -qry`（CI 用的）打一遍，42,638,371 / 42,741,204，都没有三倍。排除。
2. **Flutter 版本** —— 本机 3.47.9，与 workflow 里的 `FLUTTER_VERSION` 一致。排除。
3. **内容本身** —— 1.21.3 的 zip 里各框架字节数与今天构建的一致（FlutterMacOS 30,067,072、Harfbuzz 13,517,360…）。排除"依赖变大"。
4. **线上资产的结构** —— 用 HTTP Range 只读 zip 的中央目录（声明 `Accept-Ranges: bytes`，取末尾 64 KB 定位 EOCD，再取 79,425 字节的中央目录）：**535 项、解压后 317,977,661 字节**，而本机干净产物是 **326 项 / 107,932,996 字节**。多出来的项全部是 `Versions/Current/` 下的副本（173 项、104,551,438 字节），外加 `X.framework/X` 这一层同样被写成真文件。
5. **本机复现** —— `cp -RL` 把链接解开后 bundle 从 103 MB 涨到 301 MB，打包 123,651,586 字节。量级与线上一致。

根因：`.app` 里 `X.framework/X` 与 `X.framework/Versions/Current/X` 本来是指向 `Versions/A/X` 的符号链接。`actions/upload-artifact` 的往返不保留链接，下载回来时它们已经是三份真文件；发版步骤里的 `zip -qry -y` 这时救不回来 —— `-y` 只对"当前还是链接"的项生效。

修法（`.github/workflows/flutter.yml`）：

- macOS 构建 job 末尾先 `ditto -c -k --norsrc --keepParent` 打成 zip，再交给 `upload-artifact`。上传的就是用户最终拿到的那一份，中间不再经过"目录往返"。
- 发版 job 对 macOS 改成**原样复制**这份 zip，不再对目录重新打包；复制后立刻用 `tool/check_macos_zip.py` 复核一次。

影响：macOS 下载 124,150,561 → 约 42.6 MB（−65.7%），解压后 318.0 → 107.9 MB。顺带消除的还有一处结构错误：包里原本有三份同名 dylib 躺在只有一份该在的位置上。

### 1.2 公开包真的不带源了（1.21.5 §5.1）

1.21.5 只传了 `--dart-define=SEEWOW_NO_BUILTIN_SOURCES=true`，那个开关管"运行时不加载"：`builtin_sources.json` 仍被打进 `flutter_assets`，20 个站的接口地址仍编在 AOT 二进制里（`lib/domain/builtin_seeds.g.dart` 是真表）。

现在五个平台的 job 各加两步（`tool/ci_public_build.sh`）：

- `prep`：构建前把源包移出工作区、把代码种子换成空表；
- `verify`：构建后扫产物 —— 源包文件、两个取样域名（`zuidapi.com`、`155api.com`，按固定字符串匹配），命中任意一条退出 1。

失败发生在上传之前，所以带源的包进不了 Release。Windows 的两步显式写 `shell: bash`（runner 自带 Git Bash，只做文件搬运与扫描，不跑 flutter）。

### 1.3 公开包的关于页会印旧版本号

`lib/app/build_info.dart` 的 `SEEWOW_VERSION` 默认值写死 `1.21.5`，而 CI 的 `flutter build` 从来没传过这个 define（只有本机 `build_macos_public.sh` 传）。所以 CI 产出的公开包在关于页显示的是 `1.21.5 (dev)` —— 1.21.5 那一版就已经是这样，只是没人从产物里看过。

修法：

- 默认值跟 pubspec 同步到 1.21.6，`flutter run` 之类不传 define 的场景不会再印错；
- `prep` 顺带写 `build/public_defines.json`（`SEEWOW_VERSION` 取 pubspec，`SEEWOW_BUILD_STAMP` 取 `<短哈希> <UTC 时间>`），五个平台的 build 统一用 `--dart-define-from-file=build/public_defines.json` 读同一份 —— 不依赖各 shell 的变量语法（Windows 的 pwsh 和 bash 写法不同，写进 build 行里迟早出错）。

验证：用 CI 的原样命令在本机构建一次，构建戳字符串能在 AOT 二进制里搜到（§5 第 8 条）。

| 闸门 | 红向证据（本机跑出来的） | 绿向证据 |

macOS 那份是这次的重点：**42,724,754 字节 / 326 项 / 解压 108.9 MB**，对照 1.21.5 的 124,150,561 / 535 项 / 318.0 MB。本机重新下载后复算的 SHA256 与 Release 里的 `SHA256SUMS.txt` 一致，再用 `check_macos_zip.py` 扫一遍：0 个框架链接被写成真文件。Android 包的源包扫描在 runner 上通过（日志原文：`verify: build/app/outputs/flutter-apk/app-release.apk 干净（无源包文件、无站点地址）`）。

**发版过程记一件事**：tag 推上去的第一次运行，`macos` 与 `ios` 两个 job 排队 15 分钟后被取消，GitHub 的注解是 `The job was not acquired by Runner of type hosted even after multiple attempts`，并附「macOS arm64 runner 容量紧张，排队可能更久」；`release` 因为 `needs` 没满足而 skipped，**一个资产都没有产生**。用 `gh run rerun 45423234921 --failed` 重跑那两个 job，之后六 job 全绿、Release 建好。第一次运行没有任何产物，所以不存在「有人下到半成品」；tag 与提交也没动过。

## 5. 没做的事

1. **四个平台的 CI 没在真 runner 上验证过**：Windows / Linux / Android / iOS 的 prep、verify、以及 macOS 的打包步骤，本机只能证明 macOS 这一条链路（有真产物）。tag 打完若这些 job 红，红在构建前后、不会产出带源的包。
2. **缓存加速倍数仍未测**（沿用 1.21.5 §5.2）：只验证了 libmpv 行为与清理规则。
3. **README 与 `docs/release-index.md` 的描述还是 1.21.5**：等 Release 建好再改，否则会写出一个尚不存在的版本。1.21.5 发布说明 §3 与 §5.1 是关于旧产物的如实记录，**不回改**。
4. **iOS 仍不进 Release**：未签名包装不上，只留本机自签。

## 6. 验证（可重跑）

```sh
# 1 版本号
grep -n '^version:' apps/seewow/pubspec.yaml          # 1.21.6+32

# 2 构建前的准备与构建后的校验（任一平台参数见脚本头部）
bash apps/seewow/tool/ci_public_build.sh prep
bash apps/seewow/tool/ci_public_build.sh verify build/macos/Build/Products/Release/seewow.app

# 3 1.21.5 线上 macOS 包的中央目录（不整包下载：取末尾 64 KB 与中央目录）
U=https://github.com/sevenaaaaaaaaa/SeeWow/releases/download/v1.21.5/SeeWow-macos-1.21.5-public-nosources.zip
S=124150561
curl -sL -H "Range: bytes=$((S-65536))-$((S-1))" "$U" -o /tmp/z_tail.bin
# 中央目录偏移在 EOCD 里（本例 124071114，长度 79425），解析后应看到 535 项 / 317,977,661 字节

# 4 打包器不影响体积
cd apps/seewow/build/macos/Build/Products/Release
ditto -c -k --norsrc --keepParent seewow.app /tmp/a.zip && ls -l /tmp/a.zip
zip -qry /tmp/b.zip seewow.app && ls -l /tmp/b.zip

# 5 复现三倍：把链接解开再打包
cp -RL seewow.app /tmp/deref.app && du -sh /tmp/deref.app
ditto -c -k --norsrc --keepParent /tmp/deref.app /tmp/deref.zip && ls -l /tmp/deref.zip

# 6 本机整条链路（含版本戳、校验和、两道闸门）
bash apps/seewow/tool/build_macos_public.sh
python3 apps/seewow/tool/check_macos_zip.py dist/SeeWow-macos-1.21.6-public-nosources.zip

# 8 define 真的进了产物（本机跑 CI 的原样命令）
bash apps/seewow/tool/ci_public_build.sh prep
cd apps/seewow && flutter build macos --release \
  --dart-define=SEEWOW_NO_BUILTIN_SOURCES=true \
  --dart-define-from-file=build/public_defines.json
grep -a -o '[0-9a-f]\{7\} 20[0-9-]*T[0-9:]*' \
  build/macos/Build/Products/Release/*.app/Contents/Frameworks/App.framework/Versions/A/App | head -2
bash apps/seewow/tool/ci_public_build.sh restore     # 手工 prep 之后记得还原

# 9 tag 之后的运行
gh run list --branch v1.21.6 --limit 1
gh release view v1.21.6 --json assets --jq '.assets[] | "\(.name) \(.size)"'
```

## 7. 版本号规则

`v1.21.5` 已公开，同一个号下面不能出现第二个二进制，所以这一版是 **1.21.6+32**，tag 为 `v1.21.6`。CI 的版本闸门会比对 `pubspec.yaml` 与 tag，不一致直接失败。
