# 1.21.4 免费元数据与批量刮削（30）

> 构建：1.21.4+30 · 本地 macOS 预览包 · 上一版 1.21.3 (29) 已发到 GitHub（零源公开包）

这一版做两件事：**封面 / 作品 / 评论全部走免密钥接口**，以及**批量刮削**（一条一条补太慢，一次点完）。

## 1. 免费接口

| 场景 | 数据源 | 拿到什么 | 实测（2026-11-23） |
| --- | --- | --- | --- |
| 电影 / 剧集 / 动漫 / 短剧 | 豆瓣 `rexxar/v2/search` + `subject_abstract` + `interests` | 封面、片名、年份、评分、类型、地区、导演演员、**短评** | 流浪地球 7.9 · 甄嬛传 9.4 · 海贼王 9.5 · 我在八零年代当后妈 6.4 |
| 动漫 | AniList GraphQL | 封面、标题、简介、评分、集数、角色、**评论** | 海贼王 3 条评论，百分制归一到 10 |

被淘汰的候选（都实测过）：iTunes Search 本机恒返 0 条；Jikan / Bangumi / 中文维基在这台机器上全部超时。

**评论是新能力**：`MetadataSource.supportsReviews` + `reviews()`，不支持评论的源返回空表而不是假装查过。详情页「大家怎么说」默认折叠，点一次才发请求。

## 2. 批量刮削

入口：媒体库工具栏的「批量刮削」（齿轮右侧第二个图标）。刮的就是当前筛选出来的那批条目。

三条硬规则：

1. **只补空白**：已有海报或简介不覆盖。
2. **不碰人确认过的**：`metadata.reviewed == true` 的条目一律跳过，连请求都不发。
3. **匹配要过门槛**：片名归一化后的二元组相似度不够、或年份差一年以上，判失败也不写错海报。同名不同片（短剧 vs 电影）在豆瓣上很常见。

「同时补简介」默认关闭：简介要再发一次详情请求，整批请求量翻倍。

## 3. 豆瓣的限流，以及为什么改用 rexxar

实测出来的硬事实：

- `movie.douban.com/j/subject_suggest` 在**突发**（十几二十次）之后开始**静默返回空数组**（2 字节），不报错。约 40 秒后恢复。
- `m.douban.com/rexxar/api/v2/search` 抗突发（连打 5 次都是 24 KB 正常响应），而且**一次请求就给齐** id/片名/年份/评分/封面/地区类型导演演员。

所以搜索主路径换成 rexxar，`subject_suggest` 只当兜底；批量默认单并发 + 400 ms 间隔 + 空结果分级退避（700 ms → 1600 ms）重试两次。

改之前：5 个条目里 4 个「没有足够接近的匹配」——不是匹配算法错，是接口在装死。改之后：5 个条目 4 条命中、垃圾片名 1 条正确拒绝。

## 4. 验证

## 6. 已知缺口

- 批量刮削只补**封面/评分/类型/地区/主创/（可选）简介**，不写评论——评论按条目点开时实时拉。
- 豆瓣三支接口是页面自用的内部接口，不是官方开放 API，字段类型会漂（`region` 是字符串、`types` 是数组），解析层两种都吃。
- 批量刮削不会自动跑：仍然要用户点一次。

## 7. M1 已落地：作品级搜索（同日追加）

按 [能力规划](../product/2026-11-23-capability-plan.md) 的 M1 做完了第一刀：**搜索结果从「站点 × 条目」变成「作品」**。

| 项 | 改之前 | 改之后 |
| --- | --- | --- |
| 搜「庆余年」 | 125 行，20 个站各占几行 | **40 部作品**，第一部挂着 10 个源 |
| 一行写什么 | 片名 + 站点名 | 片名 + 年份 + `可直连 · 4K · N 个源` |
| 排序 | 按片名字典序 | 本地有货 > 能直连 > 源多 > 片名 |
| 同站重复 | 同一部片出现两次 | 按 (站点, 条目) 去重，留集数多的 |
| 需解析的源 | 与可播源混在一起 | 明确标「需网页解析」，不算可播 |

实现：`lib/sources/work_aggregator.dart`（`Work` / `WorkSource` / 聚合与排序）、`online_source_view.dart` 结果列表改为作品行 + 源列表弹层。

规则（都写成测试了）：

1. 归一化片名 + 年份做主键；年份都有且不同 → 两部片；「流浪地球2」不并入「流浪地球」。
2. `remarks`/`typeName` 里认 `4K / 1080P / 720P / HD`，认不出就空着，不猜。
3. 只有分享页的源，`headline` 必须写「需网页解析」。
4. 本地片库已有的集数计入 `localEpisodes`，并在列表排最前。

验证：`flutter test` 501 通过 / 2 跳过 / 0 失败（新增 7 条聚合用例）；真网 `tool/live_works_check.dart` 实测 125 行 → 40 部作品。

**这一刀还没做的**：豆瓣评分与评论尚未进入作品行（当前 `rating` 恒为 null）；详情页顺序、⌘K、三态首页属于 M2/M3。

### M1 收尾：豆瓣进作品行（同日追加）

`Work.rating` 不再是 null。搜索完成后，界面立刻显示作品行，再按序去豆瓣补评分/海报/简介：

| 项 | 值 |
| --- | --- |
| 补全范围 | 每次搜索最多补前 8 部（`WorkEnricher.maxWorks`），已有评分的跳过 |
| 节奏 | 每部间隔 350ms 串行；豆瓣突发限流会静默返空，串行是唯一稳的做法 |
| 匹配 | 归一化片名必须**完全相同**，年份相差 ≤1；否则留空 |
| 失败 | 单条失败只留空，不写 0 分、不写假海报 |
| 真网结果 | 搜「庆余年」：第一季 ★7.9（7 个源）、第二季 ★7.3（10 个源）；衍生剧没有豆瓣条目 → 评分为空，未编造 |

顺带修掉一个真问题：同一站会在不同分类里把同一部片吐多次、条目 id 还不同。去重键改成「同站 + 同归一化片名 + 同年份」，保留清晰度更高/集数更多的那份。

验证：`flutter test` 509 通过 / 2 跳过 / 0 失败（新增 7 条补全用例）；`tool/live_works_check.dart` 真网跑通完整链路（20 站检索 → 40 部作品 → 豆瓣补全 6 部）。

## 8. M2 已落地：详情页纵向流 + 起播器 + 失败切源

作品行点进去不再是「再弹一层选源」，而是一条纵向流：

1. **能不能看**：一行决断（`可直连 · 1080P · 7 个源`）+ 主按钮「开始看」。
2. **从哪看**：源矩阵，每源一行写清晰度/集数/直连或需解析；点一行 = 从该源起播；集数 >1 的源右侧有「选集」进原剧集列表。
3. **是什么 / 大家怎么说**：简介 + 评论（点开才拉）。

起播器 `lib/playback/work_launcher.dart` 的三条规则：

| 规则 | 行为 |
| --- | --- |
| 排序 | 沿用作品排名（直连优先、清晰度、集数），本地有货先算 |
| 失败切源 | 某个源的地址拿不到（无直链集数 / prepare 抛错）→ 自动换下一个源，最多试 3 个 |
| 记住坏源 | 失败记在作品上，下次优先跳过，源行标「上次失败」；只在内存，重启重试 |

为什么切源放在「解析层」而不是「播放器里」：播放器当前没有错误回调，而采集站失效最常见表现为地址拿不到或 4xx——在这一层切，既不猜也不假装修好了播放器。

验证：`flutter test` **518 通过 / 2 跳过 / 0 失败**（新增 7 条起播器用例 + 2 条详情页 widget 用例）；真网链路（20 站检索 → 40 部作品 → 豆瓣补全 → 起播器取直链）已在 `tool/live_works_check.dart` 跑通。

**仍未做**：播放器内的运行时错误无法回传（如中途断流），所以「播到一半换源」还做不到；这需要给 `PlayerScreen` 加错误回调，属于下一步。
